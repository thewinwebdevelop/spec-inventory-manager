## M-01 — ส่งลิงก์ทาง LINE บนมือถือจริง 🔴

**ทำไม่ได้จริง ๆ** — ต้องมีคนถือโทรศัพท์ที่มี LINE เครื่องจริง เครื่องนี้ไม่มีทั้งคู่

ที่ทำให้ได้คือ **ตัดความเสี่ยงเรื่องรูปร่างของลิงก์ออกไปก่อน** เพื่อให้คนที่ทำ M-01 ไม่ต้องมาเจอเรื่องนี้:

```
http://localhost:3001/invite?token=8Qe3wKUFL_WS80HnoMp03AoPIKcGoQGl3eDnZygwaVQ
```

token = **base64url 43 ตัว** (`A–Z a–z 0–9 - _`) — ไม่มีอักขระที่ LINE ห่อ/ตัด (ไม่มี space, `+`, `/`, `=`,
ไม่มี unicode) · path เดียว query เดียว ⇒ ที่เหลือของ M-01 คือคำถามของ LINE เอง ไม่ใช่ของเรา

⚠️ **ข้อควรระวังสำหรับคนที่จะทำ M-01:** ต้องตั้ง `WEB_APP_BASE_URL` เป็น host ที่โทรศัพท์เปิดได้จริง
(`localhost` ในลิงก์ = เครื่องที่กดเปิด) — เป็นคนละเรื่องกับ **B-17** ด้านล่างแต่พลาดแบบเดียวกันเป๊ะ

## M-02 — admin-reset ให้เจ้าของร้าน ⚠️ **คำถามที่ runbook ถาม ตอบไม่ได้ และเหตุผลหนักกว่าที่คิด**

runbook ถามว่า *"Owner ที่เจอข้อความ 404 นี้ รู้ไหมว่าต้องทำอะไรต่อ"*
**Owner ไม่มีวันเจอข้อความนี้ เพราะไม่มีจอไหนเรียก endpoint นี้เลย**

```
$ grep -rn "reset-password|resetPassword" apps/web/src apps/mobile/lib   → 0 hits
$ grep -n  "reset-password" packages/contracts/openapi/root.yaml         → มี endpoint
```

**พฤติกรรมของ API เองถูกต้อง** (ยิงตรงด้วย bearer ของ Admin จริงในร้านจริง):

| ทำอะไร | ผล |
|---|---|
| Admin รีเซ็ตรหัสให้ **พนักงาน** (control) | `200 {"ok":true}` |
| Admin รีเซ็ตรหัสให้ **เจ้าของร้าน** | `404 {"error":{"code":"NOT_FOUND","message":"ไม่พบข้อมูล","traceId":"…"}}` |
| ตามด้วย: เจ้าของร้านล็อกอินด้วยรหัส**เดิม** | `200` — รหัสไม่ถูกแตะ ⇒ fail-closed จริง ไม่ใช่ write ที่พัง |

⇒ D-030/NEW-1 ทำงานตามที่เคาะไว้ · control ที่ได้ `200` คือสิ่งที่ทำให้ `404` แปลว่าอะไรได้จริง

**เรื่องที่ต้องให้ ux + product อ่าน — ทางกู้บัญชีมีอยู่แค่ใน API:**
จอเดียวที่พูดถึงเรื่องนี้คือ `/login/help`:

> "ตอนนี้ระบบยังไม่รองรับการขอรีเซ็ตรหัสผ่านด้วยตัวเอง **กรุณาติดต่อเจ้าของร้าน/ผู้ดูแลระบบ (Owner/Admin) ในทีมของคุณ เพื่อให้ตั้งรหัสผ่านใหม่ให้**"

…แล้วเจ้าของร้าน/ผู้ดูแลที่ถูกติดต่อ **ไม่มีปุ่มให้กด** ⇒ คำแนะนำบนจอชี้ไปที่ทางที่ยังไม่มีอยู่
· ราคาที่ D-030 เคาะรับไว้คือ "ร้านที่มี Owner คนเดียวกู้เองไม่ได้" · **ของจริงตอนนี้กว้างกว่านั้น:
ร้านที่มี Owner หลายคนก็กู้ไม่ได้ เพราะไม่มีจอ**

## M-03 — คำเชิญ Owner/Admin แสดง 24 ชม. ตรงกับ `expiresAt` จริง ✅

เชิญจริง 3 ใบด้วย 3 สิทธิ์ แล้วเทียบกับแถวใน Postgres:

| สิทธิ์ | จอบอก | `expiresAt` ใน DB (UTC → ICT) |
|---|---|---|
| เจ้าของร้าน | `ลิงก์ใช้ได้ถึง 5 ก.ย. 2569 20:30 (อีกประมาณ 24 ชั่วโมง)` | `2026-09-05 13:30:51` → **20:30:51** ✅ |
| ผู้ดูแล | `ลิงก์ใช้ได้ถึง 5 ก.ย. 2569 20:31 (อีกประมาณ 24 ชั่วโมง)` | `2026-09-05 13:31:32` → **20:31:32** ✅ |
| พนักงาน | `ลิงก์ใช้ได้ถึง 11 ก.ย. 2569 20:36 (อีกประมาณ 7 วัน)` | +7 วัน ✅ |

**หลักฐานว่าไม่ใช่ค่าคงที่ที่พิมพ์ไว้ (ซึ่งเป็นสิ่งที่ M-03 ถามจริง ๆ):**
คำเชิญสองใบที่ออกห่างกัน **41 วินาที** แสดงเวลา **20:30 กับ 20:31** ⇒ ตัวเลขเดินตามเวลาที่ออกลิงก์
· และสิทธิ์ที่ต่างกันให้ TTL ต่างกัน (24 ชม. vs 7 วัน) ⇒ อ่านจาก `expiresAt` ไม่ใช่จากค่าคงที่

ตรงกันทั้ง **3 จอ**: dialog ตอนสร้างลิงก์ · แถวในรายการคำเชิญ · จอรับคำเชิญ `/invite` (ที่คนถูกเชิญเห็น)

## M-04 — "ใครรับไปแล้วเมื่อไหร่" + ธง `acceptedUserCreatedAfterInvite` ⚠️

**ครึ่งที่ผ่าน — ถ้อยคำของธง ✅**
สมัครบัญชีใหม่ด้วยอีเมลที่ถูกเชิญ (บัญชีจึงเกิด*หลัง*ลิงก์) แล้วกดรับ · แถวคำเชิญขึ้นว่า:

> **บัญชีที่กดรับถูกสร้างขึ้นหลังจากออกลิงก์ ตรวจสอบว่าเป็นคนที่คุณตั้งใจเชิญ**

อ่านแล้วเป็น "ช่วยตรวจหน่อย" ไม่ใช่ "คนนี้น่าสงสัย" ⇒ **AC-3.9 ผ่าน**

**ครึ่งที่ไม่ผ่าน — "เมื่อไหร่" ไม่มีอยู่บนจอเลย → B-15**
แถวคำเชิญที่ถูกรับไปแล้วยังขึ้นว่า `ลิงก์ใช้ได้ถึง 5 ก.ย. 2569 20:30 (อีกประมาณ 24 ชั่วโมง)`
— ลิงก์ที่ถูกใช้ไปแล้ว · `acceptedAt` อยู่ใน contract ตั้งแต่ล็อกสเปก และ**ไม่มีโค้ด production ฝั่งเว็บบรรทัดไหนเคยอ่านมันเลย**
(ดู §B-15 — แก้แล้ว)

**เรื่องที่ต้องให้ ux ตัดสิน — ธงนี้ซ่อนอยู่หลังปุ่มที่ชื่อไม่ตรงกับของข้างใน:**
คำเชิญที่ถูก**รับแล้ว**จะเห็นได้ต่อเมื่อกด **"ดูคำเชิญที่หมดอายุ/ยกเลิกแล้ว"** เท่านั้น
· คนที่เพิ่งเชิญคนเข้าร้านไม่มีเหตุผลจะไปกดปุ่มที่เขียนว่า "หมดอายุ/ยกเลิก" ⇒ **คำเตือนความปลอดภัยอยู่ในที่ที่ไม่มีใครเปิด**
· หัวข้อในกล่องเปลี่ยนเป็น "คำเชิญทั้งหมด" ถูกแล้ว — ที่ไม่ตรงคือ*ป้ายบนปุ่ม* ซึ่งเป็น copy ของ ux (ux-wireframe §7 บรรทัด 486/548)

**อีกข้อที่สเปกสั่งไว้แต่ยังไม่มี:** ux-wireframe §7 บรรทัด 525 บอกว่าแถวที่ไม่ pending ควรมีปุ่ม
**"เชิญใหม่อีกครั้ง"** ที่เปิด S7 พร้อมเติมอีเมล/สิทธิ์เดิม — ยังไม่มีในของจริง (ไม่ได้แก้ในรอบนี้ · ของ ux/product จัดลำดับ)

## M-05 — error ไทย 18 ตัว + คำว่า "ร้าน" ไม่ใช่ "องค์กร" ✅ (ครึ่งที่เครื่องตรวจได้)

| ตรวจอะไร | ผล |
|---|---|
| `"องค์กร"` ใน source ที่ขึ้นจอ (web + mobile, ไม่นับ test) | **0 จุด** |
| `"องค์กร"` ใน message ฝั่ง server | **0 จุด** (เจอ 1 ที่เป็นคอมเมนต์อธิบายกฎใน generated types) |
| **client เอา `message` ดิบจาก server มาขึ้นจอไหม** | **ไม่เลยทั้งสองฝั่ง** — web แปลง `code`→copy ของตัวเองทุก call site · mobile ไม่มี `failure.message`/`e.message` สักจุด |

ข้อสุดท้ายคือข้อที่ทำให้ M-05 ตอบได้จริง: runbook เตือนว่า "ข้อความที่ hardcode ในคอมโพเนนต์คือที่ที่มันหลุด"
— ของจริงคือ **ไม่มีเส้นทางให้สตริงฝั่ง server ไปโผล่บนจอเลย** ⇒ สิ่งที่ ux ต้องอ่านคือ copy ของ client ล้วน ๆ

**ที่ยังต้องให้ ux อ่านเอง (เครื่องตอบแทนไม่ได้):**
`apps/web/src/i18n/errors.ts` มาร์กเอง 5 ตัวว่า `‡new` = ไม่มี wireframe รองรับ (`server` · `validation` ·
`notFound` · `conflict` · และ `retry`) ⇒ ยังรอ ux ยืนยัน

**รากของมันคือรูปที่เจอซ้ำทั้งฟีเจอร์นี้:** `expiry.ts` เตือนเรื่องนี้ไว้ใน doc comment ของตัวเองว่า
*"telling somebody a dead link is live"* แล้ว `MembersScreen` ก็เรียก `formatExpiry` กับทุกแถวโดยไม่ดู `status`
— **โมดูลรู้กฎ ไม่เท่ากับจอทำตามกฎ** · `expiresAt` เป็น NON-NULL ทุกแถวตามสัญญา (ux Q14) มันจึงอ่านได้เสมอและผิดเสมอ

**แก้:** ป้ายสถานะตามที่ **ux-wireframe §7 บรรทัด 549 สั่งไว้อยู่แล้ว** (ไม่ใช่ copy ใหม่):
`รอตอบรับ · หมดอายุแล้ว · ยกเลิกแล้ว · รับแล้วเมื่อ {วันเวลา}`
· บรรทัดหมดอายุขึ้น**เฉพาะแถวที่ลิงก์ยังใช้ได้จริง** · แถวที่เลย `expiresAt` ขึ้น "หมดอายุแล้ว" ทันทีโดยไม่รอ server (§14 บรรทัด 1091)
· `acceptedAt` ถูกอ่านเป็นครั้งแรก ⇒ **ปิดครึ่งที่ขาดของ M-04 ไปด้วย**

เทสต์: `expiry.test.ts` (12) + `MembersScreen.invitation-status.test.tsx` (3 — มีเคส non-vacuity ว่าแถวเป็น ๆ ต้องยังมีบรรทัดหมดอายุ)
· red→green ยืนยันแล้ว: ถอดการแก้ออก → 2 เคสแดงทันที

## B-16 — ทั้งแอปเว็บไม่มีปุ่ม "ออกจากระบบ" ✅ แก้แล้ว

เจอตอนจะสลับบัญชีเพื่อทำ M-04 · ทางเดียวที่ออกจากระบบได้คือ **"ออกจากระบบทุกอุปกรณ์"** ที่หน้าความปลอดภัย
— คนละคำถามกันคนละเรื่อง (ฆ่าทุก session ทุกเครื่องของคนนั้น)

- **ux-wireframe §S2 วาด "ออกจากระบบ" ไว้เป็นแถวสุดท้ายของ sidebar** ⇒ สเปกมี ของไม่มี
- `orgTh.shell.nav.logout = "ออกจากระบบ"` มีอยู่ในดิกชันนารี **และไม่มีใครเรียกเลยทั้ง tree**

**แก้:** `NavAction` (แถว sidebar ที่ทำ action แทนที่จะ navigate) + เรียก `logoutDevice()` = จบเฉพาะ session นี้
· **ล้มแล้วอยู่กับที่และบอก** ไม่เด้งไป `/login` แบบหลอก ๆ (เพราะ `logoutDevice` เคลียร์ token หลังได้ `204` เท่านั้น
⇒ ถ้าล้ม session ยังอยู่ครบ การพาไปหน้า login จะเป็นการโชว์การออกจากระบบที่ไม่ได้เกิดขึ้น)

เทสต์: `AppShell.logout.test.tsx` (4) + **E-16 บนเบราว์เซอร์จริง** — กดออก แล้ว**โหลด `/` ใหม่**ต้องยังอยู่ที่ login
(ครึ่งนี้ component test พิสูจน์ไม่ได้ เพราะ refresh cookie เป็น httpOnly)

⚠️ copy ตอนล้ม (`ออกจากระบบไม่สำเร็จ ลองใหม่อีกครั้ง`) ผมเขียนจาก `logoutAllFailed` ของ ux ย่อลงมาเหลือเครื่องเดียว
— มาร์ก COPY GAP ไว้ในไฟล์ i18n แล้ว **รอ ux ยืนยัน**

## B-17 — แอปมือถือชี้ไป API ไหนไม่ได้เลย ✅ แก้แล้ว

`--dart-define=API_BASE_URL=…` ที่ทั้ง runbook และเลน CI ส่งเข้าไป **ถูกอ่านโดย
`integration_test/org_flow_test.dart` ไฟล์เดียว** · `lib/main.dart` ฮาร์ดโค้ด `http://localhost:3000` ไว้
— ซึ่งใน emulator (และบนมือถือจริง) `localhost` คือ**ตัวเครื่องเอง** ⇒ ทุก request ตาย

จอ login รายงานว่า **"เกิดข้อผิดพลาด กรุณาลองใหม่อีกครั้ง"** เพราะ `login_controller.dart` มี `catch (_)`
ที่กลืน exception ทั้งหมด (มีสตริง `errorNetwork` = "เชื่อมต่อไม่ได้ กรุณาลองใหม่" อยู่ใน ARB แต่เส้นนี้ไม่เคยใช้)
⇒ ผมเสียเวลาไล่ผิดทางไปหลายรอบ (สงสัย cleartext HTTP ก่อน — ลองแล้วไม่ใช่) เพราะข้อความมันไม่บอกอะไรเลย
· **ฝากเป็นคำถามของ ux/mobile: connection failure ควรพูดว่า "เชื่อมต่อไม่ได้" ไหม** — สตริงมีอยู่แล้ว

**ทำไม CI ถึงเขียวมาตลอด:** E-10 สร้าง provider graph เองจาก define แล้วเรียก `buildAppOverrides` ตรง ๆ
ไม่เคยผ่าน `main.dart` ⇒ **harness กับแอปต่างคนต่างสอดคล้องกับตัวเอง แล้วไม่ตรงกัน** — รูปเดียวกับที่ audit ทั้งชุดเจอ

**แก้:** `main.dart` อ่าน `String.fromEnvironment('API_BASE_URL', defaultValue: 'http://localhost:3000')`
· tripwire `test/app/base_url_define_test.dart` บังคับว่า **แอป · integration test · runbook ต้องพูดถึงคีย์เดียวกัน**
(เทสต์พฤติกรรมจับไม่ได้: `String.fromEnvironment` เป็น compile-time const) · red→green ยืนยันแล้ว
**หลังแก้: ล็อกอินบน emulator สำเร็จจริง**
