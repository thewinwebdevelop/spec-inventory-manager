# ══ Gate 1 — Requirement ══

## 1. ภาพรวม (Overview)

- **ปัญหา/เป้าหมาย:** วันนี้ (หลัง F-002) ทุกร้านมี role ตายตัว 3 ตัว (Owner/Admin/Staff) ที่แก้ไม่ได้ ร้านจริงมีหน้าที่
  หลากหลาย (แพ็คของ, แอดมินตอบแชท, คนทำบัญชีภายนอก) — F-003 ให้ร้าน **ปรับ/สร้าง role เองได้ด้วยการติ๊ก checklist
  สิทธิ์แบบกลุ่มหยาบ** โดย **ไม่เปิดช่องให้ใครยกสิทธิ์ตัวเองเกินที่มี** และ **ร้านไม่มีทางเหลือ Owner 0 คน**
- **ผู้ใช้:**
  - Owner (ถือ `full_access` — ทำได้ทุกอย่าง)
  - ผู้ถือ `manage_roles` (preset = Admin) — จัดการ role ได้ภายในขอบสิทธิ์ของตัวเอง
  - ผู้ถือ `manage_members` (preset = Admin) — มอบ role ให้สมาชิก/เชิญ ภายในขอบสิทธิ์ของตัวเอง
  - สมาชิกทุกคน (ถูก enforce) · System · Super-admin/back-office (seam เท่านั้น — F-085)
- **คุณค่า:** เจ้าของร้านมอบงานได้ตรงหน้าที่ + ปลอดภัย (ยกสิทธิ์ตัวเองไม่ได้, ล็อกร้านตัวเองไม่ได้) · ธุรกิจได้ฐาน RBAC
  ที่ทุก feature ถัดไป (สินค้า/สต๊อก/ออเดอร์/บัญชี) เสียบ capability เพิ่มได้โดยไม่รื้อ

**3 ชั้นการ gate (จาก F-007 — อย่าปนกัน):**
`ทำได้ ⇔ สมาชิก active (F-002) ∧ role มี capability (F-003) ∧ can(org, feature) (F-007)`

## 2. User stories & Acceptance criteria

> รหัส error ในวงเล็บ = **ชื่อที่ product เสนอ** เพื่อให้ AC ทดสอบได้ — `backend-api` ตั้งชื่อจริง/HTTP status
> สุดท้ายใน api-spec (Gate 2) ได้ แต่ **พฤติกรรม** (ปฏิเสธ/ไม่ปฏิเสธ, ข้อมูลอะไรกลับไป) ผูกตาม AC นี้
> "สิทธิ์ของ X" ทุกที่ในเอกสาร = ชุด capability **หลังขยาย** (`full_access` = ทุก key ใน registry · `manage_X` ⇒ `view_X`)

### US-1 · role มาตรฐานติดมาให้ (seed + backfill)
ในฐานะ **ร้านใหม่และร้านเดิม** ฉันต้องการ **role มาตรฐานที่พร้อมใช้** เพื่อเริ่มงานได้ทันทีโดยไม่ต้องตั้งค่า
- [ ] AC-1.1: สร้างร้านใหม่ → seed **3 role: Owner, Admin, Staff** ตาม preset §4.2 (ไม่มี Accountant — ร้านสร้างเองได้)
- [ ] AC-1.2: Admin ที่ seed ใหม่ **มี `manage_roles`** (capability ใหม่) เพิ่มจากชุดเดิมใน `SYSTEM_ROLE_BLUEPRINT`
- [ ] AC-1.3: **Backfill:** ทุกร้านที่มีอยู่ก่อน F-003 — role Admin ได้ `manage_roles` เพิ่ม · Owner/Staff **ไม่เปลี่ยน** ·
      รันซ้ำได้ไม่เพิ่มซ้ำ (idempotent) · มี test ว่าหลัง backfill ชุด capability ของทั้ง 3 role ตรง preset §4.2 เป๊ะ
- [ ] AC-1.4: system role เดิมคง `key` = `owner|admin|staff` · custom role ที่สร้างใหม่ `key = null` เสมอ
      (**ผู้ใช้ตั้ง key เองไม่ได้** — ไม่มี field `key` ใน request ของการสร้าง/แก้ role)
- [ ] AC-1.5: **ชื่อที่แสดง:** Owner แสดงคำแปลตาม key เสมอ ("เจ้าของร้าน") · Admin/Staff แสดงคำแปลตาม key
      **จนกว่าร้านจะเปลี่ยนชื่อ** — เมื่อเปลี่ยนแล้ว **ชื่อที่ร้านตั้งชนะคำแปล** ทั้ง web และ mobile · custom role แสดงชื่อที่ตั้งเสมอ

### US-2 · มอบ role ให้สมาชิก (ใช้ซ้ำได้)
ในฐานะ **ผู้ถือ `manage_members`** ฉันต้องการ **กำหนด role ให้สมาชิก/ผู้ถูกเชิญ** เพื่อให้แต่ละคนได้สิทธิ์ตามหน้าที่
- [ ] AC-2.1: 1 role มอบให้สมาชิกหลายคนได้ (`Membership.roleId`) · 1 คนมี 1 role ต่อร้าน · คนเดียวต่างร้านต่าง role ได้
- [ ] AC-2.2: dropdown เลือก role (จอเชิญ + จอเปลี่ยน role สมาชิก) แสดง **custom role ด้วย** · role ที่ผู้ใช้ **มอบไม่ได้**
      (ตาม US-5) แสดงเป็น **disabled พร้อมเหตุผลสั้น ๆ** ไม่ซ่อน — ทั้ง web + mobile
- [ ] AC-2.3: การตัดสิน "มอบได้ไหม" อยู่ที่ server เสมอ — client ส่ง role ที่มอบไม่ได้มา → ปฏิเสธ (US-5) แม้ UI จะไม่ได้ disable
- [ ] AC-2.4: แก้ capability ของ role → มีผลกับ **ทุกคนที่ถือ role นั้นที่ request ถัดไป** (ไม่ต้อง logout · ไม่รอ token หมดอายุ)
- [ ] AC-2.5: **การมอบ / เชิญ / ออกลิงก์ใหม่ / ถอดสมาชิก ยัง gate ด้วย `manage_members` เหมือน F-002** — ไม่เปลี่ยน gate ของ route ที่ ship แล้ว ·
      เพิ่มแค่กฎ ⊆ (US-5) ซ้อนเข้าไป · `manage_roles` = **ออกแบบ role เท่านั้น** (สร้าง/โคลน/แก้/ลบ/ดูรายละเอียดสิทธิ์) ไม่ได้ให้สิทธิ์มอบ role
      _(user ตัดสิน 2026-09-26)_

### US-3 · สร้าง / โคลน / แก้ / ลบ role
ในฐานะ **ผู้ถือ `manage_roles`** ฉันต้องการ **จัดการ role ด้วยการตั้งชื่อ + ติ๊กสิทธิ์** เพื่อให้ตรงกับหน้าที่จริงในร้าน
- [ ] AC-3.1: **สร้าง** role = ชื่อ + ติ๊ก capability จาก checklist (§4.1 — เฉพาะที่ไม่ถูกซ่อนด้วย tier tag)
- [ ] AC-3.2: **โคลน** role ที่ผู้ใช้มีสิทธิ์อ่านแบบแก้ได้ (US-5) → ฟอร์มสร้างที่เติม capability ไว้ + ชื่อเสนอ "สำเนาของ …" ·
      **ไม่มีปุ่มโคลน Owner** (ผลคือ role ที่ถือ `full_access` ซึ่งห้ามตาม US-4)
- [ ] AC-3.3: **แก้** ชื่อ/capability ของ Admin, Staff, custom role ได้ · Owner แก้ไม่ได้ (US-4)
- [ ] AC-3.4: **ชื่อ role ไม่ซ้ำในร้าน** — เทียบแบบตัดช่องว่างหัวท้าย + ไม่สนตัวพิมพ์ใหญ่เล็ก → ซ้ำ = ปฏิเสธ (`ROLE_NAME_TAKEN`) ·
      ความยาว 1–50 ตัวอักษร (นับ code point · ตัดช่องว่างหัวท้ายก่อนนับ) _(user เคาะ 2026-09-26)_
- [ ] AC-3.5: _(user เคาะ 2026-09-26)_ ชื่อ role ห้ามตรงกับ **ชื่อที่แสดงของ system role** ในร้านเดียวกันด้วย (เช่น สร้าง
      custom ชื่อ "เจ้าของร้าน" ไม่ได้) — กัน role Staff ที่ตั้งชื่อหลอกให้ดูเหมือนเจ้าของ
- [ ] AC-3.6: role ต้องมี **capability ≥ 1** → ว่าง = ปฏิเสธ (`ROLE_EMPTY`) · capability ที่ไม่มีใน registry = ปฏิเสธ (`UNKNOWN_CAPABILITY`)
      — ไม่เก็บ key แปลกปลอมลง DB เด็ดขาด
- [ ] AC-3.7: **เพดาน role ต่อร้าน = 30** (รวม system role) — เกิน = ปฏิเสธ (`ROLE_LIMIT_REACHED`) _(user เคาะ 2026-09-26)_
      (env-tunable แบบ `MAX_ORGS_PER_USER` ของ D-029)
- [ ] AC-3.8: **ลบ role** ได้เฉพาะเมื่อ **ไม่มีสมาชิก `active` ถืออยู่ และไม่มีคำเชิญ `pending` ชี้อยู่** → ไม่งั้นปฏิเสธ `409 ROLE_IN_USE`
      พร้อม **จำนวน** `{ activeMembers: n, pendingInvitations: m }` (ตัวเลขเท่านั้น — ไม่ส่งชื่อ/อีเมล · ดู Compliance) ·
      **ไม่มี bulk reassign** — ผู้ใช้ย้ายสมาชิก/ยกเลิกคำเชิญเองก่อน · UI แสดงจำนวน + ทางไปจอสมาชิก/คำเชิญ
- [ ] AC-3.9: _(user เคาะ 2026-09-26)_ คำเชิญ `pending` ที่ **หมดอายุแล้ว** ก็นับใน `pendingInvitations` (เพราะ reissue ปลุกกลับได้)
- [ ] AC-3.9b: _(user ตัดสิน 2026-09-26)_ role ที่เหลือแค่ **ประวัติ** ชี้อยู่ — สมาชิก `revoked` / คำเชิญ `accepted` หรือ `cancelled` —
      **ลบได้ ไม่บล็อก** · ประวัติเหล่านั้นต้องยังอ่านได้ไม่พัง (เช่น จอคำเชิญที่รับแล้วยังแสดงชื่อ role เดิมได้) · กลไก (soft-delete / FK nullable ฯลฯ)
      = `backend-api` เลือกใน Gate 2
- [ ] AC-3.10: **แก้ role ของตัวเองจนเสียสิทธิ์** (เอา capability ที่ตัวเองใช้อยู่ออก เช่น `manage_roles`) → client **เตือนก่อนยืนยัน**
      (บอกชัดว่าจะเสียสิทธิ์อะไร) · server ไม่บล็อก (Owner กู้คืนได้เสมอเพราะ Owner ล็อก — US-4)
- [ ] AC-3.11: ก่อนบันทึกการแก้ capability → client แสดง **"มีผลกับสมาชิก N คน"** (N มาจาก server)
- [ ] AC-3.12: **แก้ชนกัน** — สองคนแก้ role เดียวกันพร้อมกัน → คนหลังได้ `409 ROLE_CHANGED` ให้โหลดใหม่ ·
      **ห้าม last-write-wins เงียบ** (capability เป็นเรื่องความปลอดภัย การเขียนทับเงียบ = สิทธิ์ที่ไม่มีใครตั้งใจ)

### US-4 · Owner ล็อก + ร้านต้องมี Owner เสมอ
ในฐานะ **ระบบ** ฉันต้องการ **ให้ Owner แตะไม่ได้ และ `full_access` อยู่ได้ที่เดียว** เพื่อไม่ให้ร้านล็อกตัวเองหรือถูกยึด
- [ ] AC-4.1: role Owner (`isSystem=true`): **เปลี่ยนชื่อไม่ได้ · แก้ capability ไม่ได้ · ลบไม่ได้** — ทุกเส้นทางเขียน → ปฏิเสธ (`ROLE_LOCKED`)
      ไม่ว่าผู้เรียกเป็นใคร (รวม Owner เอง)
- [ ] AC-4.2: **`full_access` มีได้เฉพาะบน role Owner ที่ล็อกเท่านั้น** — สร้าง/แก้/โคลน role ที่มี `full_access` → ปฏิเสธ
      (`FULL_ACCESS_RESERVED`) · `full_access` **ไม่แสดงใน checklist**
- [ ] AC-4.3: **invariant "Owner active ≥ 1 คน" ต้องเป็นจริงหลังทุกเส้นทางที่เขียน role** (สร้าง/แก้/ลบ/backfill/migration) —
      ไม่ใช่แค่เส้นทางที่แตะ membership · server ต้องมี **ตัวตรวจเชิงป้องกันใน tx เดียวกับการเขียน** แม้ AC-4.1/4.2 จะปิดช่องไว้แล้ว
      (defense-in-depth) + **test ที่พิสูจน์ว่าตัวตรวจนี้แดงได้จริง** (กลไก เช่น `OwnerChange` รูปที่สาม = Gate 2 ของ backend-api)
- [ ] AC-4.4: กฎ F-002 คงเดิม: เฉพาะ Owner ที่มอบ role Owner / แก้-ถอด membership ของ Owner ได้ · Owner คนสุดท้ายออก/ถูกถอดไม่ได้ (`LAST_OWNER`)

### US-5 · กันยกสิทธิ์เกินตัว (privilege-superset — NEW-10 + ส่วนที่เหลือของ D-030)
ในฐานะ **เจ้าของร้าน** ฉันต้องการ **ให้คนที่ช่วยจัดการทีมให้ได้เฉพาะสิทธิ์ที่เขามีเอง** เพื่อไม่ให้ใครใช้ role ยกตัวเองหรือพวกพ้องขึ้นมาเกินที่ฉันตั้งใจ
- [ ] AC-5.1: **กฎหลัก:** ผู้ใช้ (ที่ไม่ใช่ Owner) **สร้าง / โคลน / แก้ / ลบ / มอบ** ได้เฉพาะ role ที่ **capability ⊆ สิทธิ์ของตัวเอง** ·
      การแก้ต้องผ่านทั้ง **ชุดก่อนแก้ ⊆ ของตัวเอง** และ **ชุดหลังแก้ ⊆ ของตัวเอง** → ไม่ผ่าน = ปฏิเสธ (`ROLE_EXCEEDS_ACTOR`)
- [ ] AC-5.2: role ที่มี capability **ใดก็ตาม** นอกสิทธิ์ของผู้ใช้ = **อ่านอย่างเดียวสำหรับผู้ใช้คนนั้น** — ดูได้ แต่แก้/ลบ/โคลน/มอบไม่ได้ ·
      UI แสดงไอคอนล็อก + เหตุผล "role นี้มีสิทธิ์ที่คุณไม่มี" (ทั้ง web + mobile)
- [ ] AC-5.3: "มอบ" ครอบ **ทุกเส้นทาง** ที่ผูกคนกับ role: เปลี่ยน role สมาชิก · สร้างคำเชิญ · ออกลิงก์คำเชิญใหม่ (reissue) —
      ทุกเส้นทางเรียก **กฎเดียวกันจาก `core-domain`** ไม่มีสำเนาที่สอง
- [ ] AC-5.4: _(user เคาะ 2026-09-26 · ต่อยอดจากกฎหลัก)_ ผู้ใช้ **เปลี่ยน role / ถอด / ยกเลิกคำเชิญ** ของคนที่ **role ปัจจุบัน ⊄ สิทธิ์ตัวเอง**
      ไม่ได้ — รูปเดียวกับที่ F-002 ห้าม Admin แตะ Owner (ขยายจาก "Owner" เป็น "ใครก็ตามที่สิทธิ์เกินเรา") · gate ของ route ยังเป็น `manage_members` (AC-2.5)
- [ ] AC-5.5: **Admin reset password (D-030 ส่วนที่เหลือ — user ตัดสิน 2026-09-26):** ผู้ใช้ที่ไม่ใช่ Owner รีเซ็ตรหัสสมาชิกได้
      **เฉพาะเมื่อสิทธิ์ของเป้าหมาย ⊊ สิทธิ์ของผู้รีเซ็ต (subset แท้)** — เท่ากัน, มากกว่า, หรือตัดกันไม่ครอบ (เป้าหมายมี capability ใดที่ผู้รีเซ็ตไม่มี)
      → ปฏิเสธด้วย **404 รูปเดิม** (404-never-403 เหมือน C-2/NEW-1) · Owner ยังเป็นไปตาม D-030 เดิม (Owner รีเซ็ต Owner ด้วยกันได้) ·
      เงื่อนไขเดิมทั้งหมด (C-2 หลายร้าน, High-2 ห้ามรีเซ็ตตัวเอง) คงอยู่
- [ ] AC-5.5b: ⚠️ **เปลี่ยนพฤติกรรมของ route ที่ F-002 ship แล้ว** (`POST /orgs/{orgId}/members/{userId}/reset-password`):
      **Admin → Admin ที่สิทธิ์เท่ากัน ซึ่งวันนี้รีเซ็ตได้ จะถูกปฏิเสธ** (404 รูปเดิม — wire/contract ไม่เปลี่ยน) · ต้องมี
      **regression test ที่ระบุชื่อกรณีนี้ตรง ๆ** (Admin→Admin เท่ากัน = 404 · Admin→Staff ⊊ = ผ่าน · ตัดกันไม่ครอบ = 404 · Owner→Owner = ผ่าน)
      + บันทึกใน changelog §6 · copy ฝั่ง client ที่เคยบอกว่า Admin รีเซ็ตให้ Admin ได้ (ถ้ามี) ต้องแก้ในรอบเดียวกัน
- [ ] AC-5.6: Owner (`full_access`) ผ่านกฎ ⊆ ทุกข้อ (สิทธิ์ = ทุก key) แต่ **ยังติด AC-4.2** (มอบ `full_access` ผ่าน custom role ไม่ได้)
- [ ] AC-5.7: การเทียบใช้ **สิทธิ์ปัจจุบันของผู้ใช้ ณ ตอนเขียน** อ่านใน tx เดียวกับการเขียน — ไม่ใช่ค่าจากตอนเปิดจอ
- [ ] AC-5.8: test matrix บังคับ (unit, `core-domain`): อย่างน้อย ⊂ / = / ⊃ / ตัดกันไม่ครอบ (incomparable) / ว่าง / มี `full_access` /
      มี key ที่ถูก imply (`manage_X` ⇒ `view_X`) — ทั้งฝั่ง role CRUD, assign, invite, reissue, reset

### US-6 · บังคับสิทธิ์ที่ทุก API ฝั่ง server
ในฐานะ **ระบบ** ฉันต้องการ **ให้ทุก endpoint โดเมนตรวจ capability ก่อนแตะข้อมูล** เพื่อให้ UI ที่ซ่อนปุ่มไม่ใช่ security
- [ ] AC-6.1: ทุก route โดเมนประกาศ capability ที่ต้องใช้ (ต่อยอด `@RequireCapability` ของ F-002) → ไม่มีสิทธิ์ = 403 ก่อนแตะข้อมูล
      (ยกเว้น route ที่ contract กำหนด 404-never-403 อยู่แล้ว)
- [ ] AC-6.2: ทุก capability ที่ route อ้าง **ต้องมีใน registry** — อ้าง key ที่ไม่มี = test แดง (กันพิมพ์ผิดแล้วกลายเป็น deny-all เงียบ ๆ หรือกลับกัน)
- [ ] AC-6.3: ตรวจสิทธิ์ใน scope ร้าน active เท่านั้น (กฎทอง 3) · cross-org leak int-test ของ route ใหม่ทุกเส้น (บังคับตาม F-002)
- [ ] AC-6.4: route จัดการ role: อ่านรายละเอียด capability ของ role = ต้องมี `manage_roles` · เขียน = `manage_roles` + US-5 ·
      `GET /roles` เดิม (ทุกสมาชิก active อ่านได้) **ยังไม่ส่ง `capabilities`** ออกไป (คงหลักการ F-002)
- [ ] AC-6.5: **ไม่มี cache membership/สิทธิ์ใน F-003** — resolve จาก DB ทุก request · ถ้า feature ไหนจะเพิ่ม cache ต้องมี invalidation ตอน
      revoke/แก้ role + test "แก้แล้ว request ถัดไปเห็นผลทันที" (forward-commitment คงไว้)

### US-7 · capability registry ที่ขยายได้ + tier tag
ในฐานะ **ระบบ** ฉันต้องการ **registry กลางของ capability** เพื่อให้ feature ใหม่เสียบสิทธิ์เพิ่มได้โดยไม่รื้อ
- [ ] AC-7.1: registry อยู่ที่เดียว (`core-domain`) — แต่ละ key มี: ป้ายไทย · คำอธิบาย 1 บรรทัด · กลุ่ม · **tier tag** (`all` | `full`) ·
      ความสัมพันธ์ imply (ถ้ามี) · client ทั้งสองฝั่งใช้ชุดเดียวกัน (ไม่ hard-code string ซ้ำ — ต่อยอด `capability-lint` ของ F-002)
- [ ] AC-7.2: เพิ่ม capability ใหม่ = เพิ่ม key ใน registry (ไม่ migrate schema) · **role เดิม default deny** · Owner ได้อัตโนมัติผ่าน `full_access`
- [ ] AC-7.3: **กฎ imply: `manage_X` ⇒ `view_X`** — ผู้ถือ `manage_X` ผ่านการตรวจ `view_X` เสมอ · ติ๊ก `manage_X` ใน UI = `view_X` ติดตาม
      (แสดงติ๊กล็อก) · `view_*` เพิ่มเข้า registry **เมื่อ feature ที่ต้องใช้มาถึง** (F-003 ไม่สร้างล่วงหน้า ยกเว้น `view_financials` ที่มีอยู่แล้ว)
- [ ] AC-7.4: capability ที่ tier tag = `full` (เช่น `access_accounting`) **ซ่อนจาก checklist** และสร้าง/แก้ role ให้มี key นี้ไม่ได้
      (`UNKNOWN_CAPABILITY` หรือเทียบเท่า) จนกว่า F-007 จะมา · **การบังคับ `role ∩ tier` จริง = F-007** (forward-commitment §7)
- [ ] AC-7.5: _(user ตัดสิน 2026-09-26)_ capability ของ feature ที่ **ยังไม่มี** (tier `all` — เช่น `manage_billing`, `manage_channels`) **แสดงใน checklist
      พร้อมป้าย "เร็ว ๆ นี้"** และ **ติ๊กล่วงหน้าได้** (มีผลทันทีที่ feature นั้นเปิด โดยไม่ต้องแก้ role ซ้ำ) · registry มีสถานะ live/upcoming ต่อ key ·
      capability tier `full` ยังซ่อนตาม AC-7.4 · กฎ ⊆ นับ key ที่ "เร็ว ๆ นี้" ด้วยเหมือน key ปกติ

### US-8 · cross-org boundary สำหรับ back-office (seam — ไม่ build)
ในฐานะ **ระบบ** ฉันต้องการ **แยก super-admin ออกจาก role ในร้านตั้งแต่แรก** เพื่อไม่ให้ RBAC ในร้านกลายเป็นทางข้ามร้าน
- [ ] AC-8.1: registry **ไม่มี capability ใดที่ให้สิทธิ์ข้ามร้าน** · `full_access` = ทุกอย่าง **ภายในร้านนั้น** เท่านั้น
- [ ] AC-8.2: super-admin (F-085) **ไม่ใช่ Role/Membership** — ไม่มีโค้ดใน F-003 ที่สร้าง actor แบบนี้ · query ข้ามร้าน = ข้อยกเว้นที่ประกาศชัด + audit (F-005)

- ไม่มี Owner "คนเดียว" แบบพิเศษ — Owner หลายคนได้ (F-002) · ทุกคนแก้ role Owner ไม่ได้เหมือนกัน

### 4.4 Edge cases
| กรณี | พฤติกรรมที่คาดหวัง |
|---|---|
| Admin เอา `manage_roles` ออกจาก role Admin (role ตัวเอง) | เตือนก่อนยืนยัน (AC-3.10) → บันทึกได้ · Admin ทุกคนเสียสิทธิ์ request ถัดไป · Owner ยังแก้คืนได้ |
| Admin แก้ role Admin เพิ่ม `manage_billing` | ปฏิเสธ `ROLE_EXCEEDS_ACTOR` (Admin ไม่มี `manage_billing`) |
| Admin เปิดดู role ที่ร้านสร้างไว้ซึ่งมี `manage_billing` | เห็นแบบอ่านอย่างเดียว + เหตุผล · ปุ่มแก้/ลบ/โคลน/มอบ disabled |
| ส่ง `full_access` มาใน body ของ custom role (bypass UI) | ปฏิเสธ `FULL_ACCESS_RESERVED` + event ปฏิเสธ |
| ส่ง key มั่ว/`access_accounting` มา | ปฏิเสธ — ไม่เก็บลง DB |
| ลบ Staff ที่ยังมีสมาชิก 2 คน + คำเชิญค้าง 1 | `409 ROLE_IN_USE {activeMembers:2, pendingInvitations:1}` |
| ลบ role ที่เคยถูกใช้ (มีสมาชิก revoked / คำเชิญ accepted/cancelled ชี้อยู่) | **ลบได้** (ไม่บล็อก — AC-3.9b) · ประวัติต้องยังอ่านได้ — กลไก (soft-delete / FK) = backend-api Gate 2 |
| Admin รีเซ็ตรหัส Admin อีกคน (สิทธิ์เท่ากัน) | **404** (เดิม F-002 ผ่าน) — เปลี่ยนพฤติกรรมโดยตั้งใจ (AC-5.5b) · Owner รีเซ็ตให้แทน |
| Admin รีเซ็ตรหัส Staff (Staff ⊊ Admin) | ผ่าน (ถ้าเงื่อนไข C-2/High-2 ผ่าน) |
| Staff ที่ร้านให้ `manage_members` รีเซ็ตรหัสคนที่มี `manage_billing` | **404** — สิทธิ์ตัดกันไม่ครอบ |
| ลบ role Admin/Staff ทั้งคู่ | ได้ ถ้าไม่มีคนใช้ · ร้านยังมี Owner · สร้าง role ใหม่ได้ตามเพดาน |
| เปลี่ยนชื่อ Staff เป็น "พนักงานแพ็คของ" | แสดง "พนักงานแพ็คของ" ทุกที่ (ชื่อชนะคำแปล) · `key` ยังเป็น `staff` แต่ไม่ถูกใช้ตัดสินสิทธิ์ (G-12) |
| ร้านเดิมที่ยังไม่ได้ backfill (รันไม่ผ่าน) | Admin ใช้หน้า role ไม่ได้ (ไม่มี `manage_roles`) แต่ Owner ใช้ได้ — fail closed ไม่ใช่ fail open |

## 5. Compliance note (PDPA — light)
- **ข้อมูลส่วนบุคคลที่แตะ:** `Membership` (userId ↔ ร้าน ↔ role) · `Invitation.email` (นับจำนวนเท่านั้น) · event actor id · Role เอง **ไม่ใช่** ข้อมูลส่วนบุคคล
  (ยกเว้นร้านตั้งชื่อ role เป็นชื่อคน — ยอมรับได้, เตือนใน copy ไม่จำเป็น)
- **Minimization:** `409 ROLE_IN_USE` ส่ง **จำนวน** ไม่ส่งชื่อ/อีเมล — ผู้ถือ `manage_roles` ที่ไม่มี `manage_members` ต้องไม่เห็นรายชื่อสมาชิก/อีเมลผ่านทางอ้อม
  (คง D-028 N-4: รายชื่อ + อีเมล = `manage_members`) · ตัวนับ "มีผลกับสมาชิก N คน" (AC-3.11) ก็เป็นตัวเลขเท่านั้น
- **"แก้ไขล่าสุดโดย" (AC-9.6):** เปิดเผย **ชื่อที่แสดง** ของผู้แก้ให้ผู้ถือ `manage_roles` — ไม่แสดงอีเมล (อีเมลยังเป็นของ `manage_members` ตาม D-028) ·
  ผู้แก้ที่ออกจากร้านแล้วแสดง "อดีตสมาชิก" (ไม่เผยตัวตนคนที่ไม่ได้อยู่ในร้านแล้ว)
- **Audit payload:** เฉพาะ id (actorUserId/orgId/roleId) + ชื่อ role + capability — ไม่มีอีเมล/ชื่อคน/IP เกินที่ event เดิมมี
- **Retention:** event วันนี้เป็น structured log (ไม่มีที่เก็บถาวร) — retention ตามนโยบาย log ของ devops จนกว่า F-005 จะมี store + นโยบายเก็บ
- **Purpose:** RBAC เป็นมาตรการความปลอดภัยตาม PDPA ม.37(1) — การแยก `view_financials` / `manage_members` ช่วย need-to-know

### 8.2 แนวทางที่แนะนำ + trade-off
1. **Capability หยาบ ≤ ~12 ตัว แบ่งกลุ่มตามงานจริง** (ทีม / ร้าน / สินค้า-สต๊อก / ช่องทางขาย / ออเดอร์ / การเงิน) —
   *trade-off:* ร้านที่อยากได้ "แก้ราคาได้แต่ลบสินค้าไม่ได้" ทำไม่ได้ · *ทำไมยอม:* SME non-tech ตั้ง 40 ช่องไม่ถูก และ
   ตั้งผิด = ช่องโหว่ · ความละเอียดเพิ่มทีหลังได้ด้วยการแตก key (default deny ทำให้ปลอดภัย)
2. **กฎ ⊆ + read-only พร้อมเหตุผล** แทนการซ่อน — *trade-off:* Admin อาจสับสนว่าทำไมแก้ไม่ได้ · ถ้าซ่อนจะหนักกว่า
   (คิดว่าระบบพัง/หาไม่เจอ — บทเรียน F-002 "หาไม่เจอ ≠ ไม่มี")
3. **Owner ล็อกเต็ม + `full_access` ที่เดียว** — *trade-off:* ร้านที่อยากได้ "เกือบ Owner" ต้องติ๊กทุกช่อง (ยกเว้น `full_access`) ·
   ได้คืน: invariant Owner ≥ 1 ไม่ต้องพึ่งตัวตรวจอย่างเดียว · ความสามารถใหม่ที่เพิ่มในอนาคตไม่รั่วไปหา "เกือบ Owner" (default deny)
4. **แสดงผลกระทบก่อนบันทึก** ("มีผลกับ 3 คน" + diff ที่เพิ่ม/ลบ) + เตือนเสียสิทธิ์ตัวเอง — ต้นทุนต่ำ ลดความผิดพลาดของคนไม่สาย tech มาก
5. **ไม่มี bulk reassign / ไม่มี override รายคน ในรอบนี้** — ลด surface ความปลอดภัยครึ่งหนึ่ง · ร้านเล็ก (1–10 คน) ย้ายทีละคนได้
